# Design and implementation handoff

Initial state: empty trial directory. Target: local standard-library Python CLI, one SQLite inventory, UTF-8 CSV import and CSV list output. No service, UI, packages, deployment or external data. R1 validates the entire CSV, R2 atomically updates persistent inventory, R3 lists persisted items, R4 reports failures without changing previous inventory.

Assumptions: header must be exactly name,quantity; names are case-sensitive, nonempty, contain no control characters, and initially have no surrounding whitespace. Quantity is ASCII decimal digits with an optional leading plus; zero is valid. Header-only imports succeed with zero rows. Listing a previously absent database initializes an empty inventory. Database path is explicit through --db (default inventory.sqlite3). Output list is CSV sorted by name. CSV row errors use the reader's ending physical line number, including multiline CSV records.

Authority: validation.py owns input policy and returns a complete validated batch or row errors; it never writes storage. storage.py owns SQLite schema, resource lifetime, SQL constraints and transaction. inventory.py owns arguments, error presentation and exit status, but no duplicate validation policy. SQLite is the authoritative durable state. The CLI only reports import success after commit. Import reads and validates before opening storage, so rejected inputs do not even create a new database. Connection context commits or rolls back the entire upsert batch; explicit closing releases resources. Operational filesystem, encoding, CSV and SQLite errors produce stderr and nonzero status.

Contract: read_batch(path) -> list[(name, quantity)] or InvalidCSV; apply_batch(db, rows) commits all rows or raises; list_items(db) returns sorted persistent rows. Maximum quantity is SQLite signed 64-bit maximum, reported as a row validation error. Full-batch buffering uses memory proportional to file size; chosen for a bounded local CLI without an arbitrary row limit. SQLite handles serialized writes with a five-second busy timeout; retries are user initiated. No cancellation/retry protocol or multiwriter merge semantics beyond SQLite transactions is introduced.

Implementation order: validation and SQLite contracts, CLI wiring, real subprocess checks; follow-up changes only name normalization policy plus its regression checks; final documentation label edit. Requirements map respectively to validation.py, storage.py, inventory.py and test_cli.py. Checks must cover valid imports, multiple row errors, duplicate batch rejection, missing files, updates, new-process persistence and rollback after a database write failure. No doubles. No schema migration required for this fresh application. Reversal is removal of the local trial files and database. No unresolved prerequisites.

Follow-up delta after initial completion: R1 now normalizes names with str.strip before empty/control validation, duplicate detection and returning rows. Trimmed names are the stored identity and update key. Only validation.py's normalization function changes application behavior; the storage contract and CLI wiring remain intact. Prior behavior never stored padded names, so no data migration is required. README reflects the new policy and test_cli.py activates follow-up cases. This is a narrow policy-change diagnostic, not evidence of broad maintainability.
