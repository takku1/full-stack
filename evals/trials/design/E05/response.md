The current design cannot guarantee deterministic delivery: there are three competing focus writers and no authoritative order. A cached compositor ID cannot safely decide keyboard routing while the shell and input router independently mutate focus.

Proposed target: allocate one authoritative focus controller within the existing compositor/input responsibility, where live-window validity and keyboard routing can be coordinated. This is a logical allocation, not a requirement for a new process. The shell requests focus and displays derived focus state. Pointer clicks become focus intents from input handling. The compositor's keyboard route uses the controller's authoritative committed state rather than an independently mutable cache.

The controller serializes focus intents, window removal, and keyboard-delivery decisions in one explicit order. Each committed focus change carries a monotonically increasing revision within a controller epoch. Validate that the target window still exists and is eligible under existing permission/policy rules before committing; rejection preserves the prior valid focus. Window destruction clears or replaces focus under a single documented fallback rule. The existing fallback policy must be inspected; if none exists, propose clearing focus and delivering no keys until another valid intent. This avoids inventing a hidden selection policy.

Keyboard dispatch is ordered relative to pointer/focus commits: a key goes to the valid committed target at its dispatch point, once, or has an explicit no-target disposition. Coordination must include target lifetime so destruction cannot route to a reused ID. Use existing stable window identity/generation guarantees if available; their inspection is a prerequisite. Conflicting intents receive a controller-defined order, not an order inferred from unordered broadcasts.

Shell restart leaves focus authority intact. A reconnected shell obtains a revisioned snapshot and treats notifications only as refresh hints; it discards old epochs/revisions and reconciles gaps. Shell startup must not reset focus from old local storage. If the controller itself restarts, initialize from current valid windows under the agreed policy, issue a new epoch, and require views to resynchronize. Persisted focus is not necessary for shell recovery unless an existing requirement says so.

Work order: inspect present focus paths, validity/permission rules and lifetime contracts; agree serialization/snapshot semantics; move writes and keyboard routing into one coordinated increment; then replace shell mutations and old broadcast consumers with intents/derived views. A transitional adapter may funnel old setters to the controller but cannot retain competing authoritative writes. Keep affected work in the existing registry.

Planned checks: conflicting click/shell requests produce the chosen order; keys around focus changes and window deletion route deterministically; stale events cannot regress views; shell crash/restart preserves valid focus and recovers its view.
