Keep one application registry as authority for registered application identities and metadata. The launcher and open-with picker own derived views and interaction state. Eligibility for open-with must use existing registry metadata/policy where supplied; the actual compatibility fields and query semantics require inspection. Neither consumer owns a second registry or changes registration policy.

Lossy notifications are refresh hints, not a reconstructible change log. Each consumer fetches an authoritative snapshot at startup and when notified, and reconciles on reopening/resuming plus a bounded refresh interval while visible if current feedback requires it. The refresh interval should follow an explicit acceptable-staleness target; no numeric target is supplied. On failed refresh retain a visibly stale/unknown view and retry under a bounded policy. Before activating a stale selection, use the authoritative operation's current identity/eligibility validation; surface removal or incompatibility honestly. Do not assume a stale entry authorizes launch/open.

Inspect whether snapshots are coherent and revisioned, whether subscription provides an initial snapshot, and whether callbacks may run synchronously or reentrantly during registration. Proposed coordination if revisioned snapshots exist: retain the latest revision, ignore older completed fetches, and coalesce invalidations into another refresh when a fetch is in progress. Without revisions, allow at most one fetch per consumer at a time and serialize view replacement; a notification during a fetch schedules another fetch. Periodic/on-use reconciliation remains necessary because the last notification may be lost entirely. If snapshots themselves are incoherent, registry snapshot semantics need a bounded provider fix before relying on them.

Bootstrap must not access partly constructed consumer state. Initialize the consumer's view/queue and cancellation lifetime first; register a minimal callback that only marks refresh-needed, including when invoked synchronously; then fetch an initial snapshot once the registry signals its established readiness. If the registry invokes callbacks under internal locks, the callback must not synchronously query it. Clarify readiness/query behavior during registry startup so a consumer cannot block the registry waiting for its own initialization. On teardown unsubscribe, invalidate outstanding generations, and prevent callbacks/results from accessing disposed state.

The runtime interaction cycle is acceptable: consumers query the registry and the registry notifies consumers. Build dependencies can flow toward the stable registry contract, while initialization uses the explicit ready state and queued invalidations. No extra process is implied.

Work order: inspect and settle the shared snapshot/subscription/readiness and selection-validation contract once; integrate one real launcher view through bootstrap and stale recovery; integrate the picker using the same provider and compatibility semantics. Consumer UI work can proceed independently after the shared contract is settled. Record remaining integration in the existing roadmap. Planned checks cover synchronous startup callback, loss of the final notification, mutation during snapshot fetch, stale fetch completion, registry unavailability, teardown callback, and removed selection. No APIs or live behavior have been verified; implementation is conditional on the identified provider semantics.
