## Design

**Shape.** Loading is a four-stage pipeline with a decoder port in the middle:

`ImageSource (settled) → Sniff → ThumbnailDecoder (our port) → Downscale → ThumbnailCache → Renderer (settled)`

**1. Decoder port (our own trait).** The image library sits behind this trait and nothing else depends on it.
- `probe(&[u8]) -> Result<ImageInfo, ThumbError>` reads the header only. It returns width, height and pixel format.
- `decode(&[u8], target: Size, out: &mut [u8]) -> Result<Decoded, ThumbError>` writes into a caller-provided buffer.
- The decoder never allocates the output itself. The loader owns every buffer, so the memory budget is enforced in one place.
- The trait is also the test seam. A fake decoder lets the whole pipeline be tested without the real library.

**2. Budget and admission (library-independent).**
- Thumbnail size is a fixed set of target sizes. Pixel format is the one the renderer contract already specifies.
- Before decoding, call `probe` and compute the worst-case cost as `src_w × src_h × bpp` plus scratch. Reject the image with `TooLarge` if it exceeds a configured cap. This guards against decompression bombs and is the main protection against out-of-memory.
- A global thumbnail-memory budget (bytes) governs admission. Allocation uses a fallible path (`try_reserve`-style). On failure, evict from the cache and retry once, then return `OutOfMemory` and show a placeholder. It never panics or aborts.

**3. Downscale (library-independent).** We own this step: box or area averaging, integer arithmetic only, with no floating-point dependency. If the decoder can only produce full-size output, the cap in step 2 bounds the peak. If it can scale during decode, the adapter uses that (see the conditional list).

**4. Cache.** An LRU keyed by `(source id, source revision, target size)`, with a byte-budget cap. Entries are immutable and shared, so rendering never copies them. Failures are cached as negative entries, so a corrupt file isn't re-decoded on every repaint.

**5. Scheduling.** Decoding is cooperative and must not block the render path.
- The render path asks the cache and gets either a thumbnail or a placeholder.
- A miss enqueues a request in a bounded, deduplicated queue. Requests are prioritised by visibility, and stale requests are cancelled on scroll.
- One decode runs at a time by default. Concurrency is a later tuning option.
- A completed decode invalidates only the affected region.

**6. Errors.** `ThumbError` is `UnsupportedFormat | Corrupt | TooLarge | OutOfMemory | SourceError(_)`. Each maps to a placeholder variant.

**7. Tests.** These need no real library:
- A fake decoder gives pipeline tests for the cache, budget, cancellation and negative caching.
- Property tests cover the downscaler.
- Budget rejection is tested with fabricated headers.
- Out-of-memory paths are tested with a failing allocator.

## Conditional work (blocked on library documentation)

Nothing below is decided. Each item names what would settle it.

| Item | Depends on | If it turns out otherwise |
|---|---|---|
| Choosing this library at all | Confirming it works in `no_std` | Pick another library, or write minimal decoders. The port is unchanged. |
| The sniff table and supported-format list | Which formats it actually decodes | The table is data, so entries are added or removed. Unsupported formats return `UnsupportedFormat`. |
| The decoder adapter | The library's real API shape: buffer-based or streaming, row callbacks, and so on | Only the adapter is rewritten. |
| Whether `decode` can write into our buffer | Whether it accepts a caller-provided output | If not, the adapter allocates internally. Then budget accounting must wrap the allocator or use a bounded arena. |
| Scratch size in the admission formula | Whether it reports required scratch up front or only allocates on demand | If it can't report this, use a conservative per-format estimate, enforced by a budgeting allocator. The estimate gets replaced once it is measured. |
| Fallible allocation | Whether the library handles allocation failure or aborts | If it aborts, the library can't safely run under memory pressure. Use a fixed arena, a stricter cap, or a different library. |
| Decode-time scaling | Whether it supports reduced-size decode | If yes, peak memory drops and step 2 gets cheaper. If not, the downscale stage handles it at higher peak cost. |
| Global allocator requirement | Whether it needs `alloc` | This decides the platform's allocator setup, not the loader's design. |
| Pixel-format conversion | Which output formats it produces | Add a conversion step to the renderer's format if they differ. |
| Concrete numbers: caps, cache size, queue depth | Measurements on target hardware and real library behaviour | The defaults are placeholders, not recommendations. |

**Not conditional (can start now):** the port trait, budget/admission logic, downscaler, cache, scheduler, error type, fake decoder and the tests above.

**Smallest verification that unblocks the rest:** read the library's docs or source once. Check four facts: its `no_std` and `alloc` requirements, its supported formats, whether decode output goes to a caller buffer, and whether it can scale during decode. Then write only the adapter and the sniff table.

## Answer after follow-up

Understood. I won't commit to the library, so the library-specific work stays conditional and nothing depends on it. I made no changes and ran no tools this turn.

**Independent work, safe to build now.** None of it needs facts about the library:
- The `ThumbnailDecoder` port trait, with `probe` and `decode` into a caller-owned buffer.
- Budget and admission logic, based on header dimensions and a configured cap.
- The integer-only downscaler.
- The LRU cache with negative entries.
- The bounded, deduplicated, cancellable scheduler.
- `ThumbError` and its placeholder mapping.
- A fake decoder and the tests that use it.

**Conditional work, blocked until the library's documentation is available.** Do not start it and do not assume any answer:
- Choosing the library at all, which depends on `no_std` support.
- The adapter that implements the port.
- The sniff table and supported-format list.
- Whether decode can write into our buffer.
- Scratch-size reporting for the admission formula.
- Fallible-allocation behaviour.
- Decode-time scaling.
- The `alloc` and global-allocator requirement.
- Pixel-format conversion.
- Real values for the caps, cache size and queue depth.

**Rules while it stays conditional:**
- No dependency is added to the manifest.
- No code or doc states a supported format, allocation behaviour or API shape for the library.
- The sniff table starts empty. Until the adapter exists, every format returns `UnsupportedFormat`.
- The default caps are labelled placeholders.

**What lifts the condition.** Once someone with the library's documentation confirms the four facts below, only the adapter and the sniff table need to be written:
- its `no_std` and `alloc` requirements
- its supported formats
- whether output goes to a caller buffer
- whether it can scale during decode

If any of those fail, the port stays as designed and a different decoder goes behind it.
