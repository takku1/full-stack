# Image-thumbnail loading for the no_std desktop

I kept this design in chat. The working directory holds only the [skill] skill package. It has no desktop source, no `ROADMAP.md` and no design note, so there was nothing to ground against or file into. I wrote no files and ran no checks.

## Scope

- **Outcome:** the desktop shows thumbnails for image files by loading, decoding, downscaling and handing off pixels.
- **Settled, not reopened:** the image source contract and the rendering contract. I haven't seen their text, so I refer to them as "Source" and "Renderer" and invent no signatures.
- **Proposed library:** the one fact I can state is that its supported formats and allocation requirements are unknown. I did no browsing and made no claims from memory.
- **Excluded:** full-size image viewing, animation, an on-disk thumbnail cache, new formats beyond whatever the library turns out to support, and any change to the Source or Renderer contracts.

## Ownership and contracts

The first four components are new and proposed. The Source and Renderer are existing and settled.

| Component | Owns | Does not own |
|---|---|---|
| **Source** (existing) | Bytes of the image and its identity | Decoding |
| **Thumbnail loader** (new) | Request lifecycle, the cache-key-to-state map, cancellation, memory budget | Pixel decoding, drawing |
| **Decoder port** (new, a trait owned by us) | `decode(bytes, max_dim, out_buffer) -> Result<Dims, DecodeError>` | Any library types |
| **Decoder adapter** (new, conditional) | Maps the proposed library onto the port | Policy |
| **Renderer** (existing) | Display of a finished pixel buffer | Loading state |

- **State authority:** the loader owns thumbnail state: `Absent`, `Loading`, `Ready(buffer)` and `Failed(reason)`. The Renderer only consumes what the loader hands it, and a copy held by the Renderer is never authoritative.
- **Behavior, from trigger to result:**
  1. A thumbnail becomes visible and the loader receives a request keyed by the Source's identity.
  2. It fetches bytes from the Source and decodes them through the port.
  3. It downscales to the thumbnail size, stores the result, and notifies the Renderer.
- **Failure and recovery:**
  - A decode error becomes `Failed`, and the Renderer shows a placeholder. There is no automatic retry for a corrupt or unsupported file.
  - A Source error is retried per the Source contract, if it defines retry.
  - Scrolling away cancels a pending request. A decode already running finishes and its result is discarded if the key is no longer wanted.
  - Restart begins empty, because nothing is persisted.
- **Resource bounds (our policy, independent of the library):**
  - The loader enforces a global byte budget with eviction of the least recently used `Ready` thumbnails.
  - Concurrent decodes are capped at a configured number, which defaults to 1.
  - Input larger than a configured size is rejected before decoding.
- **no_std obligations:**
  - Allocation goes through our own allocator or a caller-provided arena, and the port takes a caller-provided output buffer.
  - Allocation failure is a `DecodeError::OutOfMemory`, never a panic.
  - There is no `unsafe` in the loader. Any `unsafe` stays confined to the adapter and is audited there.

## Choices

- **Decoder port as our own trait (chosen, ready).**
  - This isolates the library, which is unverified. The loader can be built and tested against the port regardless of which decoder is eventually used.
  - It sacrifices a little indirection.
  - Revisit it if the port ends up having exactly one trivial implementation after the library is verified.
- **Adopting the proposed library (unresolved).**
  - Evidence: none.
  - The unknowns are the supported formats, whether it works in no_std, whether it needs `alloc`, its allocation pattern and peak memory, and its license.
  - Alternatives are a different library or a minimal in-house decoder for one format. I won't compare them without evidence, and I am not inventing candidates.
- **Fixed-size thumbnails, decode to full size and then downscale (default, reversible).**
  - This is simplest, but peak memory is the full image.
  - If the library supports scaled decoding, that is a later optimization.

## Blockers and conditional work

- **Conditional on the library documentation:**
  - T5, T6 and the format support claim.
  - The decision to adopt the library.
  - The thumbnail memory budget defaults, since the peak allocation is unknown.
  - Whether scaled decoding is available.
- **Questions T4 must answer** (otherwise the design stays conditional):
  1. Does it support `no_std`, and does it require `alloc`?
  2. Which formats does it decode?
  3. What is the allocation pattern and peak memory for a given image size?
  4. Can it decode into a caller-provided buffer?
  5. What is its license?
- **Not blocked, but unverified:** T3 depends on contract text I haven't read, so I made no assumptions about it.
- **Assumption and cost if false:** I assumed the Source can supply bytes or a bounded stream per image. If it can only stream with no length hint, the pre-decode size check in the loader moves into the adapter.

No costly-to-reverse commitment is made here, because adopting the library is exactly what I left conditional.

## What stays conditional

- The adoption decision and the adapter (T5), including its dependency manifest entry.
- The claims about supported formats, no_std and allocator fit, and peak memory.
- The default values for the thumbnail memory budget and the concurrency cap. They are placeholders until a real decoder's footprint is measured.
- Any real thumbnail display (T6). Until T5 exists, a passing test with the T1 double proves loader behavior only. It cannot close the requirement for real image decoding.

## What the design now delivers

Without the library, the loader is fully specified and buildable against the decoder port, and the port is the only seam where a decoder attaches. The design never names or depends on the library's types. Any decoder that meets the port contract can fill that seam, including this library, if it is later adopted on verified evidence, or another one.
