## Outcome
A desktop component loads images as thumbnails and hands them to the renderer as pixel buffers of a bounded size. It works under `no_std` with `alloc`, if `alloc` is available (see Blockers).

**Excluded:**
- Changing the source or rendering contracts.
- Full-size image viewing.
- Any claim about the image library's formats, features, or allocation behavior.

## Ownership and state
| State | Owner |
|---|---|
| Encoded bytes | The image source (settled). The loader borrows them and never retains them past decode. |
| Decoded thumbnail pixels | The thumbnail cache. The renderer reads them through the settled contract. |
| Cache entries (key → `Loading`, `Ready`, or `Failed(reason)`) | The thumbnail cache, with a fixed byte budget and LRU eviction. |
| Decoder state | Short-lived and owned by the loader. It is dropped after each decode. |

The decoder sits behind a trait I'm calling `ThumbDecoder` (name not final):

```rust
trait ThumbDecoder {
    fn decode(&mut self, src: &[u8], max_edge: u32, out: &mut PixelBuf)
        -> Result<ThumbMeta, DecodeError>;
}
```

The rest of the design depends only on this trait. The proposed library becomes one implementation of it.

## Choices
1. **Hide the library behind `ThumbDecoder`.**
   - Nothing about the library is verified, so this keeps its facts out of the cache, scheduling, and failure logic.
   - A different library, or a stub, can replace it without touching those parts.
2. **Fixed memory budget.**
   - The cache has a hard byte cap, and a single thumbnail has a maximum pixel size (`max_edge² × bytes per pixel`).
   - A decode that would exceed the cap fails with `TooLarge` rather than allocating.
   - I would set `max_edge` and the cap from the rendering contract, which I can't see.
3. **Load one image at a time, off the render path.**
   - Requests are queued and deduplicated by key.
   - The renderer sees `Loading` and shows a placeholder.
4. **Failure and restart behavior.**
   - Unsupported format, corrupt data, and out-of-memory all become `Failed(reason)`.
   - A `Failed` entry is not retried automatically. A retry happens only if the source reports changed bytes.
   - Retry rules for transient source errors belong to the source contract, so I defer to it.
   - The cache is in memory only, so a restart starts empty and reloads on demand. Persisting thumbnails to disk is out of scope.

## Conditional work
Everything in increment 3, and these decisions, wait on facts I couldn't verify:
- **Supported formats:** which formats go in the user-facing list, and the `UnsupportedFormat` mapping.
- **Allocation:** whether the library can decode under `no_std`, needs `alloc`, accepts a caller-supplied buffer, or can bound its allocations. This decides whether the memory cap in choice 2 is enforceable inside the decoder or only checked before and after a decode.
- **Downscaling:** whether the library can decode directly at reduced size. If it can't, the full-size decode peak can exceed the cap, and the design needs a header-only size check first.
- **Library selection:** whether the library is acceptable at all. If it can't meet the allocation requirements, replace it. The design above doesn't change.
