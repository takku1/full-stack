# Image-thumbnail loading design for a no_std Rust desktop

**Workspace check:** the workspace contains only the skill file (`SKILL.md`), with no Rust code, `Cargo.toml` or contract definitions. I therefore have no interface or path names to cite. I refer to the settled image-source and rendering contracts only by role and invent no signatures. Nothing here was built or run.

## Outcome
Given a thumbnail request, take encoded bytes from the image source, decode them, scale them to the thumbnail size, and hand the pixels to the renderer. A bad image shows a placeholder and never takes down the desktop.

**Excluded:**
- Changes to the source or rendering contracts.
- A full-size image viewer.
- Persistent thumbnail caching.
- Choosing or verifying the library's formats or allocation behavior.

## Ownership and contracts
| State | Owner |
|---|---|
| Encoded bytes | Image source, which is settled. The loader borrows them for one decode and does not retain them. |
| Decode and scale scratch memory | Loader, from a fixed-capacity arena sized at build time. |
| Finished thumbnail pixels | Loader's bounded slot table until the renderer takes them. Slot state is `Empty`, `Pending`, `Ready` or `Failed(reason)`. |
| Placeholder image | Static data in the binary. It needs no allocation, so it is always available. |

**Internal seam (new, ours):** one small `ThumbDecoder` trait with a single operation. Given a byte slice, a target size and a scratch buffer, it returns pixels, or a typed error: `UnsupportedFormat`, `Corrupt`, `ScratchTooSmall` or `TooLarge`.
- The proposed library goes only behind this trait.
- Format support and allocation facts stay confined to one adapter.
- Everything else in the design is independent of the library.

## Choices
1. **Bounded memory.**
   - The loader works in a caller-provided or static arena with a hard per-decode cap.
   - It does not assume a global allocator, because I can't verify whether the library needs one.
   - Evidence: no_std has no allocator unless the platform supplies one. That the platform lacks one is an assumption to confirm.
2. **Reject before decoding.**
   - If the library exposes dimensions cheaply, check them against the cap first and return `TooLarge` rather than fail mid-decode. This is conditional on that API existing.
   - Otherwise the adapter relies on `ScratchTooSmall`.
3. **Failure and retry.**
   - Each error maps to `Failed(reason)` and shows the placeholder.
   - `Corrupt` and `UnsupportedFormat` are permanent for that source version and are not retried.
   - Only a source-level transient error (from the settled contract) allows retry, with a bounded count and no busy loop.
4. **Restart.** Nothing persists. After restart all slots are `Empty` and thumbnails are re-requested lazily, which is correct because there is no cache.
5. **Concurrency.** One decode at a time on the existing execution model, with a slot-count cap. Eviction is oldest-`Ready` first, and a slot in use by the renderer is never evicted.
6. **Cancellation.** If a request is dropped (for example, scrolled off screen) while `Pending`, the result is discarded and its scratch memory released.

## Increments, in order, with checks
Increments 1–4 and 6 are unconditional. Increment 5 is the only work that depends on library facts.

1. **Slot table and state machine.**
   - Check: host-side unit tests for transitions, eviction, cancellation, and the "never evict a slot in use" rule.
2. **`ThumbDecoder` trait, error type, and a fake decoder that returns fixed pixels.**
   - Check: tests that every error maps to `Failed` plus the placeholder.
   - The fake is only a test aid. It is not the shipped path.
3. **Arena and scratch accounting.**
   - Check: tests that exhaust the arena and confirm `ScratchTooSmall` is reported, with no panic and no leak across repeated failures.
4. **Scaling.**
   - This is our own box-filter downscale to the thumbnail size, which doesn't depend on the library.
   - Check: golden-pixel tests on small synthetic buffers.
5. **Library adapter. (CONDITIONAL)**
   - Blocked until the library's documentation or source is available and verified. Until then, the following are unknown and must not be assumed:
     - which formats it supports (this decides which `UnsupportedFormat` cases are real);
     - whether it needs a heap, and its peak scratch size (this sets the arena size);
     - whether it can read dimensions without a full decode (this decides the pre-check in choice 2);
     - whether it is truly `no_std`, and its license and maintenance status.
   - Check, once unblocked: decode real sample files per supported format, plus a corrupt file and an oversized file, on the target.
   - If verification shows the library doesn't fit, only this adapter is replaced.
6. **Wire into the settled source and renderer contracts.**
   - Check: an end-to-end test on the target or an emulator that goes from source bytes to a rendered thumbnail.
   - The adapter must be present for the real path, so the full end-to-end acceptance is conditional on increment 5. Until then it can run only against the fake.

## Open blockers and decisions
- **Blocker:** the library's documentation is unavailable (increment 5). Obtain it from the user, a vendored copy, or the source.
- **Decide:** the per-decode memory cap and the thumbnail dimensions. Both are needed for arena sizing and are not derivable from the request. I'd propose the cap only after the library's peak scratch size is known.
- **Confirm:** that the platform provides no global allocator, as assumed in choice 1.
- **Optional, not built:** a persistent thumbnail cache, and a progressive or low-resolution-first decode.

**Status:** this is a design only. No checks were run because there is no code to run them against.
