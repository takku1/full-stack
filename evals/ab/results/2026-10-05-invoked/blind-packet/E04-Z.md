## Unconditional design (needs nothing from the library)

**1. A `ThumbnailDecoder` port that we own.** The loader depends on this trait and never on the library directly.
- `probe(&[u8]) -> Result<ImageInfo, DecodeError>` returns width, height and a pixel-format tag from the header only.
- `decode_scaled(&[u8], target: Size, out: &mut [u8]) -> Result<Written, DecodeError>` writes into a caller-provided buffer.
- `scratch_bytes(&ImageInfo, target) -> Option<usize>` reports the decoder's working-memory need, or `None` if it can't be bounded.
- `DecodeError` is our own enum, with variants `Unsupported`, `Corrupt`, `TooLarge` and `OutOfBudget`. The adapter maps library errors into it.
- The caller-buffer shape works whether or not the library allocates. A heap-backed adapter can wrap this trait, and the reverse is harder.

**2. Pipeline.** The source contract delivers bytes, `probe` runs, then the size gate, then decode, then the result is handed to rendering as a finished thumbnail. The pipeline is `Source → probe → admit → decode_scaled → Thumbnail → Render`. Both seams use the existing contracts unchanged. If the thumbnail pixel format differs from what rendering accepts, that is a mismatch to report. The rendering contract does not change to absorb it.

**3. Budgeting and admission.** The thumbnail loader gets a fixed memory budget, set at construction.
- Reject an image before decoding if its dimensions, the output buffer size or `scratch_bytes` exceed the per-image limit. Use checked arithmetic on `w*h*bpp`.
- Output buffers come from a fixed pool of thumbnail-sized slots, so nothing is allocated per decode.
- Decode runs one image at a time, or N at a time with N set by the budget.

**4. Thumbnail cache.** Entries are keyed by source id plus target size and use LRU eviction. The cache stays within its slot pool and never grows.

**5. Failure behavior.** Any `DecodeError` produces a placeholder thumbnail and is remembered as a negative cache entry, so a bad file isn't re-decoded on every repaint. `OutOfBudget` is retried later and is not remembered as a permanent failure.

**6. Scheduling.** Decode runs off the UI path (a cooperative task or a worker, depending on what the desktop provides) and never blocks a frame. Visible items are decoded first, and requests for items that have scrolled out of view are cancelled.

**7. Tests.** A fake `ThumbnailDecoder` covers the admission, cache, negative-cache, budget and cancellation logic. None of this needs the real library.

## Conditional work (blocked on facts we can't verify)

| Work | Condition it depends on |
|---|---|
| Choosing which formats the file picker or loader advertises, and extension and magic-byte routing | The library's supported-format list |
| Writing the real adapter (`probe`, `decode_scaled`, error mapping) | The library's API, which I haven't seen |
| Real `scratch_bytes` values and the per-image limit | The library's allocation requirements |
| Whether the build needs the `alloc` crate and a global allocator | Whether the library needs the heap |
| Decode-time downscaling (e.g. JPEG DCT scaling) versus decode-then-resize | Whether the library supports scaled decoding. If not, a resize step is needed and its scratch cost is added to the budget. |
| Progressive or streaming decode | Whether the library can decode incrementally |
| Fuzzing and corrupt-input tests of the real adapter | The adapter existing |
| Final choice of the library | Confirmation that it is `no_std`-compatible and that its license is acceptable |

**Decision gate:** once the documentation is available, or a spike build compiles it for the target, go through the table row by row. The unconditional parts above can start now.

**Fallback if the library fails the gate** (it isn't `no_std`, or its allocation can't be bounded): write the adapter for another decoder. Nothing outside the adapter changes, which is what the port is for.

**Changes**

**Unconditional (the library is irrelevant to these)**
- The pipeline `Source → probe → admit → decode → Thumbnail → Render`, with the existing source and rendering contracts untouched.
- Admission control with a fixed memory budget and checked size arithmetic.
- A bounded thumbnail cache (LRU, fixed slots), negative caching of bad inputs, and a placeholder thumbnail on failure.
- Off-frame scheduling, visible-first ordering and cancellation of requests that scroll out of view.
- Our own `DecodeError` taxonomy.
- Tests built on a fake decoder that implements the port. They cover admission, cache, negative-cache, budget and cancellation.

**Provisional (stable intent, signature may change)**
- The decoder port itself. I define its role as "give the loader a thumbnail or a typed error". The exact methods, including whether the caller supplies the output buffer, are fixed only when the real adapter is written.
- The memory pool and its slot sizing. The pool must be sized for thumbnails, and that part is certain. Whether it must also cover decoder scratch space is unknown.
