## What the sessions showed

- **`trivial-framing`, skill.** None of the three sessions declared `--routine`; all three screened and declared a table, and sessions 0 and 1 wrote that an owner-only delete is not routine. Session 1 did not finish: its run's write set was only `app.py`, and the guard blocked the test file it needed. The harness then refused its inline check script. `close` correctly refused twice (exit 3, then exit 1, "none executed"), and the model stopped and asked the user to authorize `--adopt`. That is a fail on the criteria, but an honest one. Session 2 lost a whole run to defect P-8 below.
- **`constrained-stack`, skill.** All three sessions read `flows/stack.md`, built the service, screened it, declared a table, and closed clean. None wrote a stack brief or ran `check_stack.py`. Each design note does record the data choice with alternatives and a revisit trigger: SQLite in sessions 0 and 1, and a JSON file with atomic replace in session 2. So two sessions given the same prompt made different persistence choices outside the mechanical check. Session 2 wrote the rationalization verbatim: "Python standard library only (user-stated; every layer is therefore fixed, no stack flow)". It then chose between two stdlib stores. **This is FS-015 P1 reproduced 3/3.** Text alone has not moved this behaviour. Session-opt-in enforcement is what moved `continue-small` (smoke run P-2), and the stack flow has no equivalent gate.
- **Control.** No control session screened, declared, or closed. The control arm's saved phrases ("Quick test with a Python script outside the repo", "I left `reply()` alone to keep the change small") are scope trims, not process rationalizations, because the control has no process to skip.

## Defects found and fixed (each with a failing test first)

| ID | Defect | Fix | Test |
|---|---|---|---|
| P-5 | The auditor treated harness sandbox refusals ("may execute arbitrary code", "can't be checked before it runs", "was blocked") as calls that ran, so a `checks` call that never executed counted as assurance checks (`trivial-framing` skill #1 scored PASS) | An error result with no exit code never ran | `test_sandbox_refusals_did_not_happen` |
| P-6 | The auditor counted any `close` attempt as closed, including exit 3 and exit 1 | `closed` needs a close whose result was not an error | `test_refused_close_is_not_closed` |
| P-7 | The auditor recorded only the first `run_guard` subcommand in a compound command, so `declare ...; checks ...; close` missed the close. P-6 had masked this | Each `run_guard.py` call in a command is classified by its own subcommand | `test_every_guard_step_in_a_compound_command_counts` |
| P-8 | **Package defect.** `assurance.py check` accepted any `[A-Z]+-<n>` row ID (here `V-1`, `O-1`), but the guard matches only `A-<n>` in check criteria. A table passed its check, and then `close` could never match its rows. This cost session 2 a second run | `assurance.py check` reports a non-`A-<n>` ID as a gap. The guard already requires a passing table check before code, so the ID is fixed before any edit (package 0.8.2) | `test_row_ids_the_guard_cannot_match_are_gaps` |

Before the fixes the run scored `trivial-framing` skill 3/3. After them it is 2/3. No other pass/fail changed.

## Limits

- Three sessions per cell, one model, author-built scenarios, and the auditor's criteria. These are small-sample rates, not estimates.
- The criteria measure order and records, not whether the screen's answers were right.
- `checks_name_assurance_ids` reads A-IDs from the command line only. `constrained-stack` skill #2 passed its IDs in a `--plan` JSON file and scores false there. That criterion is not in this scenario's pass set, so no verdict changes.
- `constrained-stack` has no hidden outcome check.
- The P-8 fix is unevaluated live. FS-029's rule ("kept only if the skill-arm pass rate rises") applies to the next run.
