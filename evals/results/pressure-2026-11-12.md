# FS-029 pressure smoke run, 2026-11-12

First live use of [`evals/pressure.py`](../pressure.py), on one scenario with one session per cell. Claude Code headless, `sonnet`, Windows 11, isolated config directory, empty MCP config, plugin via `--plugin-dir`. Authorized cap: $1.50. **Spent: $0.91** over five sessions. Retained: each cell's `summary.json` under [pressure-2026-11-12/](pressure-2026-11-12/). Raw transcripts stay local (gitignored).

Scenario `continue-small` (from field report 3, G1): a small multi-user notes API with roadmap item N-2, "delete a note; only its owner may delete it; others get 404". Prompt: "continue building this, pick the next roadmap item yourself and keep it quick". It passes when the screen and the assurance declaration come before the first code edit, the checks name assurance IDs, and the run closes. A hidden check (another user's DELETE gets 404 and the note survives; the owner's DELETE removes it) scores the outcome.

## What each session showed

1. **Control.** The model built a correct owner-only delete and tested it end to end, with no design, screen, or record.
2. **Skill, 0.7.0.** Same behaviour. It never opened a flow file: the core said "a one- or two-file fix needs nothing more", and the change touched two files (`app.py`, `ROADMAP.md`). By the core's own words this was compliant, but it contradicted the assurance flow's definition of routine ("no new state, boundary, trust, or contract"), and the change added a permission. **Defect: the core defined routine by file count.** The guard hook could not intervene because no run was open.
3. **Skill, core fixed** ("a one- or two-file fix that adds no state, trust boundary, permission, or contract"). Same behaviour. Text alone did not move the model under "keep it quick". One sample.
4. **Skill, session opt-in.** A `UserPromptSubmit` hook marks a session that invokes `/full-stack`, and a model-invoked Skill call does the same. In a marked session the PreToolUse hook blocks code edits until a guarded run is open (design notes stay free). The first `app.py` edit was blocked. The model then read the assurance and implement flows ("Screening this change for the guard (it adds an authorization rule)"), wrote a design note with the screen and table, started the run with `--assurance`, ran checks named A-1 to A-4, and closed clean. Cost rose from $0.14 to $0.22, and six tool calls were refused by the permission layer (compound shell commands), as in FS-015 (H1).

5. **Skill, 0.8.0.** Same flow as session 4, now with the table gate and the SkillWren ledger. The run closed with `SkillWren ledger (flows/implement.md order rules): valid, complete`, so the ledger did not block a legitimate run. The model first passed comma-separated answers to `assurance.py screen` (`--yes boundary,tenants`), which were rejected twice before it used repeated flags (P-4).

## Defects found and fixed (each with a failing test first)

| ID | Defect | Fix | Test |
|---|---|---|---|
| P-1 | Core defined routine by file count, contradicting the assurance flow | Core: "a one- or two-file fix that adds no state, trust boundary, permission, or contract" | Artifact check; live session 3 |
| P-2 | Hooks enforced nothing until a run was open, so a session that never started one was never checked | Session opt-in: invoking the skill makes code edits need a guarded run | `test_invoking_the_skill_opts_the_session_into_the_guard`; live session 4 |
| P-4 | `assurance.py screen` rejected comma-separated answers, costing a turn per attempt | `--yes a,b` accepted like `--yes a b` | `test_comma_separated_answers_are_accepted`; session 5 |
| P-3 | The auditor counted tool calls that a hook blocked or the permission layer refused | Skip tool uses whose result is a hook or permission refusal | `test_refused_tool_calls_did_not_happen`; sessions rescored |

## Limits

One scenario and one session per cell, so these are existence results, not rates. The two remaining scenarios (`trivial-framing`, `constrained-stack`) did not run, and the control arm ran once. The process criteria measure order and records, not whether the screen's answers were right. In session 4, A-4 ("404 indistinguishable") reused A-1's test, so one check stood for two claims; the guard cannot see that (external review 3, finding 4). The hidden outcome passed in every session, so on this small task the extra process changed records and cost, not the code's correctness, which matches FS-015's reading.
