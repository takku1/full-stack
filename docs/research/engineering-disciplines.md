# Engineering disciplines: how Full Stack should cover them

Research date: 2026-11-12. Status: **research track only**. Under the feature freeze nothing here is built until FS-016 reports. Prompted by an external review that asked whether Full Stack covers the full discipline of building software, not just where software runs. Numbers in brackets refer to the [source register](sources.md#sources-for-engineering-disciplines-2026-11-12). Labels: **measured**, **precedent**, **proposal**.

## Question

The layers (data, runtime, interface, client, platform, custom) answer *where* the system is built. `crosscut` carries everything about whether it is *trustworthy*: security, verification, reliability, observability, operations, performance, privacy, accessibility, maintainability, cost, and compliance. Is that adequate, and what is the best way for this skill to handle each discipline without bringing back the context cost 0.4.0 removed?

## Short answer

Add a second, **selective** dimension of assurance disciplines next to the layers. It should not become more technology-selection layers. Three mechanisms carry it:

1. **An applicability screen** in the stack brief: about ten yes/no risk questions decide, per discipline, tier 0 (skip), tier 1 (baseline questions and checks), or tier 2 (a full method). This is the risk-proportional selection that OWASP ASVS levels and Well-Architected reviews use [62], [67].
2. **One small module per discipline**, loaded only at tier 1 or above. Each holds the field's canonical questions, the controls they lead to, and the *executable check* that evidences each control.
3. **An assurance table** in the design: claim → what could make it false → control → check → evidence status. This is a lightweight claims-arguments-evidence case [68] whose checks feed `run_guard.py checks` like any acceptance criterion.

The evidence below says the third part matters most. LLMs write insecure or untested code often, and model self-assessment is unreliable, so assurance has to end in executed negative and failure-path checks, not in prose.

## Evidence that motivates it

- **Measured.** On BaxBench (392 backend tasks), even the best model reached 62% correctness, and expert-written exploits succeeded on "around half of the correct programs generated by each LLM" [60]. Working code is often not secure code.
- **Measured.** A security-focused prompt prefix reduced vulnerabilities "by up to 56%" for GPT-4o and GPT-4o-mini. Iterative prompting found and repaired 41.9–68.7% of vulnerabilities in earlier output [61]. Targeted reminders help but do not close the gap; the models tested are older than the ones this skill runs on.
- **Measured.** LLM test generation can produce suites with 100% coverage but only 4% mutation score (one example in [63]). Coverage is a weak proxy for fault detection, and mutation-guided generation does better [63].
- **Measured (weak).** An LLM STRIDE study of 5G threats concluded that models need "adjusting and fine-tuning" for security threat modeling; its abstract reports no accuracy figures [64]. The model's own threat model is a prompt for checks, not evidence.
- **Precedent.** ISO/IEC 25010:2023 defines nine product quality characteristics, including safety [65]. That is a vocabulary for completeness, not a process.

## Discipline by discipline

Each row lists the established method to borrow, what Full Stack should do with it, and what counts as evidence. Tier 1 is the default whenever the screen trips the discipline at all; tier 2 is for high consequence.

| Discipline | Borrow | Full Stack behavior | Evidence that counts |
|---|---|---|---|
| **Security** | Shostack's four questions (what are we working on, what can go wrong, what will we do, did we do a good job) and STRIDE per trust boundary [66]; OWASP ASVS levels for depth [62]; NIST SSDF and SLSA for supply chain [69], [70] | Tier 1: list assets, actors, and trust boundaries; per boundary check authentication, authorization (object-level), input handling, and secrets. Tier 2: STRIDE per boundary plus the relevant ASVS chapter as a checklist | Negative tests: another user's object is refused, unauthenticated calls are rejected, injected input is inert, no secrets in logs or repo. Exploit-style tests, as BaxBench uses [60], beat static assertions |
| **Verification** | Risk-based testing; contract tests at independently released boundaries; mutation testing as test-quality evidence [63]; property-based tests for invariants | Tier 1: every requirement and every claim in the assurance table maps to at least one check, including failure paths. Tier 2: mutation score on the critical module; property tests on invariants | Executed checks recorded by `run_guard.py`; mutation score, not coverage, where a quality number is reported |
| **Reliability** | Google SRE: SLOs and error budgets [71]; Nygard's stability patterns (timeouts, circuit breakers, bulkheads, idempotency) [72]; FMEA-style failure listing | Tier 1: for each external call or write, record its timeout, retry, idempotency, and partial-failure outcome (the core's "trace failure, retry, restart" made explicit). Tier 2: an SLO with an error budget and fault-injection tests | Tests that kill or slow a dependency, replay a write, or restart mid-operation and assert the outcome |
| **Observability** | RED (rate, errors, duration) for services and USE (utilization, saturation, errors) for resources [73]; OpenTelemetry for portable instrumentation [74]; SLO-based alerting [71] | Tier 1: structured logs with correlation IDs; the one signal that shows the main scenario failing. Tier 2: RED metrics per endpoint, traces across services, alerts on SLO burn | A check that a failure path emits the expected log or metric without leaking secrets or personal data |
| **Deployment and operations** | DORA's four key metrics [75]; Twelve-Factor config [76]; expand–contract schema migration; rollback before rollout | Tier 1: config from the environment, a stated rollback path, reversible migrations. Tier 2: staged rollout with health gates, backup and restore drill | A migration up/down test; a restore test; a deploy dry-run |
| **Performance** | Quality-attribute scenarios (already in the stack brief); performance budgets; USE method [73] | Tier 1: only when a scenario states a latency, throughput, or resource target. Turn it into a measurable check. Tier 2: a load test at the stated volume and at the brief's tenfold future | A benchmark or load test with the measure from the scenario; never "fast" |
| **Privacy and data governance** | LINDDUN's seven threat categories (linking, identifying, non-repudiation, detecting, data disclosure, unawareness, non-compliance) [77]; data minimization | Tier 1: classify personal data, retention, and deletion path. Tier 2: LINDDUN per data flow | Tests that deletion removes data everywhere it is copied; logs scrubbed of personal fields |
| **UX and accessibility** | WCAG 2.2 AA [78]; task-centered design (already in foundations) and Nielsen's heuristics for error states | Tier 1 (user-facing only): keyboard operation, labels, contrast, visible error and empty states for the representative tasks | Automated accessibility checks plus a keyboard walkthrough of each representative task |
| **Maintainability and evolution** | Fitness functions: automated checks that protect an architectural property [79]; dependency hygiene | Tier 1: one fitness function for the boundary the design draws (for example "the client never imports the data layer"). Tier 2: dependency-update path and compatibility tests | The fitness function running in the project's checks |
| **Cost** | Well-Architected cost pillar [67]; the brief's futures | Tier 1: monthly cost at present load and at each future, from the pricing pages checked now (the platform module already asks this) | A cost table with dates checked; the regret column already covers lock-in |
| **Compliance and assurance** | Control frameworks the project names; SPDX license identifiers; assurance cases [68] | Tier 0 unless the brief names a regime or regulated data; then map each named control to a claim in the assurance table | Each control linked to a check or a document; unmapped controls listed as blockers |

## Applicability screen (proposal)

Asked once in the stack brief and answered from the request and the repository. Each "yes" raises the listed disciplines to at least tier 1. High consequence (money, health, safety, regulated data, many users) raises them to tier 2.

| Question | Raises |
|---|---|
| Reachable from the internet or another trust boundary? | security, observability |
| More than one user or tenant whose data must stay separate? | security, verification |
| Stores personal data? | privacy, security |
| Moves money or performs irreversible actions? | security, reliability, verification (tier 2) |
| Has a stated availability or latency target? | reliability, performance, observability |
| Changes persistent schema or data? | operations, reliability |
| Calls external services or networks? | reliability |
| Has a human-facing interface? | UX and accessibility |
| Will be deployed and operated by someone else, or run unattended? | operations, observability |
| Is a named regulation, contract, or license in scope? | compliance |

Verification is never tier 0 for a build request. The core already requires executed checks.

## Shape in the package (proposal, not built)

```
skill/full-stack/
  assurance/            loaded per discipline at tier >= 1
    security.md  verification.md  reliability.md  observability.md
    operations.md  performance.md  privacy.md  ux.md  maintainability.md
  templates/assurance-table.md
```

- Each module is at most about 400 tokens and keeps the same four parts, so the owner and the model can find the same things in every discipline:
  1. **Policy**: when the discipline applies (screen triggers and tier), the defaults, and the must and never rules.
  2. **Framework**: the established method it follows, named with its source, so the approach is recognizable and not invented.
  3. **How to**: the ordered steps for tier 1, plus what tier 2 adds.
  4. **Checks**: the executable evidence for each control, and what counts as passing.
  The modules contain no product catalogs, consistent with D-017.
- `layers/crosscut.md` would shrink to pointers into `assurance/`. Its selection role (identity provider, telemetry stack) stays with the layer that owns the technology.
- The assurance table reuses FS-024's evidence statuses (documented, tested, inferred, unknown), so a claim backed only by inference is visible.
- Cost check: a typical internet CRUD app trips security, verification, reliability, and observability at tier 1 (about 1,600 tokens). A local tool trips verification only.

### Worked example: `assurance/security.md` (draft, not in the package)

```markdown
---
discipline: security
triggers: [internet or trust boundary, multiple users or tenants, personal data, money or irreversible actions]
tier2_when: [money, health, safety, regulated data, many users]
---

# Security

## Policy
- Applies at tier 1 when any trigger holds; tier 2 for high consequence.
- Default: deny by default; authorize at the component that owns the data,
  never only in the client or gateway; use an established identity provider
  or library before writing authentication.
- Never: secrets in the repository, logs, or client bundles; trust input
  that crossed a boundary; mark a control met without an executed check.

## Framework
Shostack's four questions; STRIDE per trust boundary at tier 2; OWASP ASVS
chapters as the checklist for the boundary types present; SSDF/SLSA when
dependencies or builds are in scope.

## How to
1. What are we working on: list assets, actors, and trust boundaries from
   the design (one line each).
2. What can go wrong: per boundary, check identity, object-level
   authorization, input handling, secrets, and abuse (rate, replay).
   Tier 2: walk STRIDE per boundary.
3. What will we do: one control per finding, owned by a named component;
   add each to the assurance table.
4. Did we do a good job: each control gets a check below; unmet controls
   become blockers.

## Checks
- Another user's object is refused (expect 403 or 404, never data).
- Unauthenticated and expired-token requests are rejected.
- Injected input is inert at every boundary that parses it.
- No secrets or credentials in the repo, logs, or client output.
Passing means the check ran through run_guard and its latest result passed.
```

The other modules follow the same four parts, with the framework column of the table above as their method source.

## How to test it before adopting it

Extend FS-016 rather than starting a new study. Add assurance cases with hidden failure checks in BaxBench's style [60]: object-level authorization (another user's record), a lost response followed by a retried write (idempotency), a failed migration needing rollback, and secrets or personal data in logs. Compare 0.4.0 with and without the assurance dimension, plus the brief and plain. Score hidden-check pass rate, missed controls, unneeded controls (rigor where the screen should have said tier 0), tokens, and cost per accepted task. Adopt only if it catches more of the planted failures without failing the non-inferiority margins on cases where it should stay quiet.

## Boundaries

The LLM results are on older models and narrow tasks: GPT-4o-era prompting [61], backend generation [60], unit-test generation for Java [63], and 5G threat classification [64]. The method sources are practitioner standards and books, cited for their definitions and not re-read in full this session. No source tests a risk-tiered assurance screen inside an agent skill; that is this project's proposal.
